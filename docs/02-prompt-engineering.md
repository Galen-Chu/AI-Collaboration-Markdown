## 什麼是 Prompt Engineering？

**Prompt Engineering** 是設計與優化輸入提示的技術，讓 AI 模型能夠：
- 🎯 產生更精準的回應
- 🧠 展現特定專業領域知識
- 💡 創造更具創意的內容
- ⚡ 提升效率並減少迭代次數

### 為什麼重要？

```
簡單 Prompt ❌
「幫我寫一個排序演算法」

優化 Prompt ✅
「你是資深軟體工程師，請用 Python 寫一個快速排序演算法，
包含：1. 詳細註解 2. 時間複雜度分析 3. 測試範例」
```

**結果差異：**
- ❌ 回籠籠統的排序程式碼
- ✅ 專業、完整、可直接使用的解決方案

## 核心原則

### 原則 1：明確性 (Clarity)

```markdown
# ❌ 模糊的 Prompt
「分析這個程式碼」

# ✅ 明確的 Prompt
「請分析以下程式碼：
1. 識別潛在的效能瓶頸
2. 標出不安全的程式碼模式
3. 提供具體的改進建議
4. 以 Markdown 表格呈現分析結果」
```

### 原則 2：情境化 (Context)

```markdown
# ❌ 缺乏情境
「如何優化這個函式？」

# ✅ 提供完整情境
「我是後端工程師，正在處理電商平台的訂單查詢功能。
這個函式會在促銷活動期間承受高流量（每秒 1000+ 請求）。
請協助優化以下程式碼，考量：
- 資料庫查詢效率
- 快取策略
- 並發處理」
```

### 原則 3：結構化輸出 (Structured Output)

```markdown
# ❌ 開放式回應
「解釋這個錯誤」

# ✅ 要求結構化回應
「請分析這個錯誤，並以以下格式回應：

## 錯誤類型
[分類：語法/邏輯/執行期錯誤]

## 根本原因
[說明錯誤發生的原因]

## 修復方案
\`\`\`language
[修復後的程式碼]
\`\`\`

## 預防措施
- [ ] 要點 1
- [ ] 要點 2」
```

## 常用模式

### 模式 1：角色扮演 (Role-Playing)

讓 AI 扮演特定專業角色，獲得專業意見。

```markdown
# 範例 1：資深架構師
「你是一位擁有 10 年經驗的資深軟體架構師，專精於微服務設計。
請審查以下系統設計，並從以下角度提供建議：
1. 可擴展性
2. 容錯���
3. 維護性
4. 成本效益」

# 範例 2：創意總監
「你是一位獲獎無數的創意總監，擅長品牌故事訴求。
請為我們的新產品設計一個感人的品牌故事...」

# 範例 3：教學導師
「你是一位經驗豐富的程式設計教師，擅長用簡單的比喻解釋複雜概念。
請用生活化的例子解釋『閉包 (Closure)』的概念...」
```

### 模式 2：思維鏈 (Chain of Thought)

引導 AI 逐步思考，提升複雜問題的解決品質。

```markdown
# 範例：除錯思維鏈
「請用思維鏈方式協助除錯：

## 步驟 1：理解問題
- 描述這個函式的預期行為
- 列出可能出錯的地方

## 步驟 2：分析證據
- 檢查錯誤訊息
- 查看相關 log

## 步驟 3：提出假設
- 基於證據，提出最可能的原因

## 步驟 4：驗證假設
- 設計測試案例
- 預期測試結果

## 步驟 5：實施修復
- 提供修復程式碼
- 說明修復原理」
```

### 模式 3：少樣本學習 (Few-Shot Learning)

提供範例，讓 AI 理解預期的輸出格式。

```markdown
# 範例：API 文件生成
「請根據以下函式產生 API 文件：

### 輸入函式
\`\`\`typescript
function calculateDiscount(price: number, tier: string): number {
  const rates = { bronze: 0.05, silver: 0.1, gold: 0.15 };
  return price * (1 - rates[tier]);
}
\`\`\`

### 輸出格式範例
\`\`\`markdown
## calculateDiscount

計算客戶等級折扣後的價格

### 參數
- \`price\` (number): 原始價格
- \`tier\` (string): 客戶等級 (bronze/silver/gold)

### 返回值
折扣後的價格 (number)

### 範例
\`\`\`typescript
calculateDiscount(1000, 'gold') // 850
\`\`\`
\`\`\`

### 現在請為以下函式產生文件：
[你的函式]」
```

### 模式 4：迭代改進 (Iterative Refinement)

透過多輪對話逐步優化結果。

```markdown
# 第一輪：初版
「請寫一個 RESTful API 來處理用戶註冊」

# 第二輪：加入驗證
「很好，請加上：
1. Email 格式驗證
2. 密碼強度檢查
3. 重複註冊檢查」

# 第三輪：加入安全性
「請再加上：
1. 輸入清洗 (Sanitization)
2. SQL 注入防護
3. 速率限制 (Rate Limiting)」
```

## 角色設定技巧

### 技巧 1：專業特質定義

```markdown
# ✅ 完整的角色定義
「你是一位 **全端工程師**，具備以下特質：

**技術專長：**
- 精通 React, Node.js, PostgreSQL
- 5 年以上實務經驗
- 專注於乾淨程式碼與最佳實踐

**工作風格：**
- 優先考慮可維護性與可測試性
- 喜歡用實際範例說明概念
- 總是提供多種解決方案並比較優缺點

**溝通方式：**
- 使用專業但易懂的語言
- 適度使用技術術語並解釋
- 主動指出潛在問題」
```

### 技巧 2：多角色協作

```markdown
# 範例：設計審查團隊
「我們組成一個設計審查團隊：

**成員 1：資深後端工程師**
- 關注：效能、可擴展性、安全性
- 角色：技術審查

**成員 2：UX 設計師**
- 關注：使用者體驗、介面一致性
- 角色：使用者體驗審查

**成員 3：DevOps 工程師**
- 關注：部署流程、監控、維運
- 角色：維運審查

請從三位成員的角度，分別審查以下設計...」
```

### 技巧 3：人格特質注入

```markdown
# 範例：特定風格的程式碼審查員
「你是一位**嚴格但建設性的程式碼審查員**，風格如下：

**個性特質：**
- 對程式碼品質要求極高
- 總是能發現潛在問題
- 批評但給予具體改進建議

**審查重點：**
1. 程式碼可讀性
2. 效能問題
3. 錯誤處理
4. 測試覆蓋率

**回應風格：**
「這段程式碼有幾個問題：
❌ [問題 1] - [具體說明]
✅ [建議] - [改進程式碼]」

請以這個風格審查以下程式碼...」
```

## 進階技巧

### 技巧 1：變數替換

使用佔位符讓 Prompt 更靈活。

```markdown
「請為 {{LANGUAGE}} 寫一個 {{ALGORITHM}} 演算法：
- 時間複雜度：{{COMPLEXITY}}
- 使用情境：{{USE_CASE}}
- 輸出格式：{{OUTPUT_FORMAT}}」

# 實際使用時替換：
「請為 Python 寫一個快速排序演算法：
- 時間複雜度：O(n log n)
- 使用情境：大數據集排序
- 輸出格式：包含詳細註解與測試案例」
```

### 技巧 2：條件式 Prompt

根據不同情境給不同指示。

```markdown
「請分析以下程式碼：

**如果這是 API 端點：**
1. 檢查輸入驗證
2. 確認錯誤處理
3. 評估安全性

**如果這是資料庫查詢：**
1. 檢查 SQL 注入風險
2. 分析查詢效能
3. 評估索引使用

**如果這是前端組件：**
1. 檢查狀態管理
2. 評估可重用性
3. 確認響應式設計」

[程式碼]」
```

### 技巧 3：輸出格式控制

精確控制回應的結構與格式。

```markdown
「請以以下 JSON 格式回應：

\`\`\`json
{
  "summary": "簡短總結",
  "issues": [
    {
      "severity": "high/medium/low",
      "type": "security/performance/maintainability",
      "description": "問題描述",
      "location": "檔案名稱:行號",
      "fix": "修復建議"
    }
  ],
  "metrics": {
    "complexity": 1-10,
    "maintainabilityIndex": 0-100
  },
  "recommendations": ["建議 1", "建議 2"]
}
\`\`\`」
```

### 技巧 4：元認知提示

要求 AI 反思自己的回答。

```markdown
「在提供答案後，請：

1. **自我評估**
   - 你對這個答案的信心程度（1-10）
   - 有哪些地方不確定？

2. **替代方案**
   - 還有哪些其他可能的解決方法？
   - 為什麼選擇這個方案？

3. **潛在風險**
   - 這個方案可能有什麼問題？
   - 在什麼情況下不適用？」

這個元認知層次的分析，能幫助你做出更好的決策。」

現在請回答原本的問題...」
```

## 實戰案例

### 案例 1：產生高品質的單元測試

```markdown
# Prompt
「你是測試驅動開發 (TDD) 的專家，請為以下函式撰寫完整的單元測試：

**函式程式碼：**
\`\`\`typescript
function parseUserInput(input: string): ParsedCommand {
  // [函式實作]
}
\`\`\`

**測試需求：**
1. 使用 Jest 測試框架
2. 涵蓋以下情境：
   - 正常輸入
   - 空字串
   - 格式錯誤
   - 邊界條件
3. 每個測試案例包含：
   - 清晰的描述
   - Given-When-Then 結構
   - 適當的斷言
4. 測試覆蓋率目標：90%+
5. 包含 setup 與 teardown」

**輸出格式：**
\`\`\`typescript
describe('parseUserInput', () => {
  // 測試案例
});
\`\`\`

並在最後說明：
- 哪些 edge cases 需要特別注意
- 如果要提升到 100% 覆蓋率還需要測試什麼」
```

## ⚠️ 常見錯誤與避免方法

### 錯誤 1：過於寬泛的 Prompt

```markdown
❌ 「寫一個好的程式碼」

✅ 「寫一個 Python 函式來解析 CSV 檔案，
要求：使用 csv 模組、處理異常、包含型別提示」
```

### 錯誤 2：忽略輸出格式

```markdown
❌ 「分析這個設計」

✅ 「分析這個設計，並以 Markdown 表格呈現：
| 組件 | 職責 | 優點 | 缺點 | 改進建議 |」
```

### 錯誤 3：一次要求太多

```markdown
❌ 「建立一個完整的電商平台，包含前後端、資料庫、
API、支付整合、會員系統、管理後台、分析報表...」

✅ 「先從核心功能開始：
請設計電商平台的產品目錄 API，
包含 CRUD 操作與篩選功能」
```

### 錯誤 4：沒有提供範例

```markdown
❌ 「產生類似的文件」

✅ 「產生類似的文件：
**參考範例：**
\`\`\`
[你的範例格式]
\`\`\`

**請為以下內容產生相同格式的文件：**
[你的內容]」
```

## 🎯 進階應用

### 應用 1：Prompt 鏈 (Prompt Chaining)

將複雜任務拆解為多個步驟，每個步驟用專門的 Prompt。

```markdown
**步驟 1：需求分析**
「請分析以下需求...」

**步驟 2：架構設計**
「基於上述分析，設計系統架構...」

**步驟 3：實作**
「根據這個架構，實作核心功能...」

**步驟 4：測試**
「為這個實作設計測試案例...」
```

### 應用 2：動態 Prompt 模板

根據回應動態調整下一個 Prompt。

```markdown
# 第一輪
「請提供 3 種解決方案」

# 根據回應選擇方案 2
# 第二輪
「請詳細展開方案 2，包含：
- 詳細設計
- 實作步驟
- 風險評估」
```

### 應用 3：多維度評估

從多個角度評估同一個問題。

```markdown
「請從以下三個角度評估這個技術選擇：

**角度 1：技術可行性**
[評估內容]

**角度 2：商業價值**
[評估內容]

**角度 3：團隊能力**
[評估內容]

**綜合建議：**
[整合三個角度的結論]」
```

## Agent Description 公式

在 [AI-Agent-Skill](https://github.com/Galen-Chu/AI-Agent-Skill) 中，我為每個 Agent 和 Skill 定義了一個三段式 Description 公式：

```
[做什麼功能]。[觸發情境/關鍵字]。[所屬層級與可重用範疇]。
```

### 為什麼三段式？

| 段落 | 影響什麼 | 範例 |
|------|---------|------|
| 第一段 | **自動路由準確度**（AI 判斷該找誰） | 「去重與摘要長文內容」 |
| 第二段 | **觸發判斷**（什麼時候該被叫） | 「當需要處理新聞、文章或報告時」 |
| 第三段 | **維護定位**（給未來的自己/團隊看） | 「③ 能力模組，跨領域可重用」 |

### 實際範例：mod-summarizer

```
 Description: 去重與摘要長文內容，產出結構化重點。當任何工作流需要
 處理多來源文本（新聞、文章、報告）時觸發。③ 能力模組，無領域判斷，
 換任何領域都適用。
```

### 好的 Prompt vs 好的 Agent Description

| 面向 | Prompt（一次性） | Agent Description（持續性） |
|------|-----------------|---------------------------|
| 生命週期 | 單次對話 | 長期存在，每次被叫都用 |
| 優化目標 | 得到好答案 | 讓 AI 能正確路由到這個 Agent |
| 包含內容 | 任務 + 情境 + 期望格式 | 功能 + 觸發條件 + 架構定位 |
| 適用場景 | 臨時需求 | 可重用的工作流步驟 |

### Skill 的 Prompt 設計原則

Skill（如 `obsidian-note-conventions`）的 Prompt 專注於**可重用的判斷邏輯**：

1. **知識與身分分離**：Skill 放判斷規則（語法、格式、評估框架），Agent 放角色定位與流程協調
2. **每次啟動不載入不必要的細節**：Agent 本體輕量，需要時才調用 Skill
3. **開源 Skill 一律改寫，不直接複製**：避免 `${CLAUDE_SKILL_DIR}` 路徑引用被破壞

## Claude Code 特有模式

### System Prompt vs User Prompt

在 Claude Code 環境中，Prompt 分為兩層：

| 類型 | 誰寫的 | 什麼時候生效 | 範例 |
|------|-------|-------------|------|
| System Prompt | Claude Code 內建/設定檔 | 每次對話 | `.claude/CLAUDE.md` 的專案規則 |
| User Prompt | 使用者輸入 | 單次對話 | 「幫我重構這個函式」 |

### CLAUDE.md 的寫法

`CLAUDE.md` 是 Claude Code 的專案級 System Prompt，效果最好 的寫法：

```markdown
# CLAUDE.md

## Commands
- npm test          # 跑測試
- npm run build     # 建置

## Architecture
- Store layer (store/) 是唯一碰 DB 的程式碼
- 不要直接改 worker/handlers/index.ts

## Conventions
- 所有 PR 都要跑過 test + lint
- 變更 model 一定要生成 migration
```

### 與 AI-Agent-Skill 的 CLAUDE 檔案比較

本 repo 的 20 文件規格中，`CLAUDE` 檔案就是為 AI Agent 設計的 System Prompt：

| 傳統 CLAUDE.md | 20 文件規格的 CLAUDE |
|--------------|-------------------|
| 一般規則 + 指令 | 同上，但明確標注受眾是 AI Agent |
| 可能混入架構說明 | 只放規則，架構放 ARCHITECTURE |
| 沒有結構化模板 | 有標準模板（見 docs/templates/CLAUDE.md） |
